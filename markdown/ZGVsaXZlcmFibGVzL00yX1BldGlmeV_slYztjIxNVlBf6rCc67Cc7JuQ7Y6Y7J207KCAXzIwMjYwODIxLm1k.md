## 1. 요약

산타바바라 카운티를 알파 파트너로 하여, **현 데모를 실데이터로 동작하는 알파 제품으로 구현**한다. 신규 설계 없이 기존 화면에 동작 기반(데이터·계산·저장·인증)을 추가하는 작업이며, 개발 2명 전담 기준 6~8주 소요를 예상한다.

## 2. 문제와 대상

| 항목 | 내용 |
| --- | --- |
| 문제 | 기존 보호소 관리 소프트웨어의 기능 부재가 원인이 아님. **보유 정보가 현장 workflow와 연결되지 않아 '다음 행동'이 누락되는 것이 원인.** 누락 1건이 동물의 보호일수 증가로 직결 |
| 대상 | 중형 공공 보호소(municipal shelter). **기존 CRM을 유지한 채 스프레드시트·회의로 진행 관리를 보완 중인 조직** |
| 현행 대체 수단 | 스프레드시트 + 주간 검토 회의. 알파 단계의 실질적 경쟁 대상은 경쟁 CRM이 아니라 스프레드시트임 |
| 확인 근거 | 산타바바라 인터뷰(2026-08-20). Director가 제품 시연 전에 스스로 문제를 제기했고, 원하는 해결 형태를 체크리스트 수준까지 구체적으로 제시 |

## 3. 제품 가설

> 조직이 **준비 완료 기준을 편집**한다 → 룰이 **상태를 자동 판정**한다 → 미충족 항목이 **대기열로 집계**된다 → 대기열 각 행에 **사유·담당자·다음 행동**을 표시한다.

- 제품의 제공 가치는 화면 통합이 아니라 **다음 단계 진행 가능 여부의 판정**임
- 이 판정 기능은 경쟁 제품군이 공통으로 제공하지 않는 영역임 (근거: 포지셔닝 문서)
- Director가 데모에서 즉시 긍정 반응을 보인 화면도 위 연쇄 구조에 따라 작동함

## 4. 알파 범위

### 4-1. 포함

| # | 항목 | 성격 |
| --- | --- | --- |
| 1 | **요건 룰 편집**: 항목별 필수 여부·경과일 기준·수량 기준 | 동작 구현 |
| 2 | **룰 계산 엔진**: 경과일·충족 여부 실계산 후 상태 자동 판정 | **신규 개발** |
| 3 | **데이터 반입**: 기존 CRM 리포트 CSV 업로드 및 필드 매핑 | **신규 개발** |
| 4 | **인증·역할**: Administrator / Reviewer / Publisher | **신규 개발** |
| 5 | 동물 목록: 현재 상태·확인 필요 사유·다음 행동·담당자 | 동작 구현 |
| 6 | 동물 상세: 상태 배너 + 요건 체크리스트 + 다음 행동 카드 | 동작 구현 |
| 7 | 확인 필요 대기열: 조직 전체에서 조치가 필요한 동물 집계 | 동작 구현 |
| 8 | 담당자 배정: 다음 행동에 담당자·마감일 지정 | 동작 구현 + 작업명 직접 입력 |
| 9 | 완료 이력: 변경·승인·상태 전환 기록 | 동작 구현 |
| 10 | 모바일 대응: 현장 확인·완료 처리 | 검증만 (반응형 구현 완료) |

- **1·2번이 제품 차별화의 핵심임.** 두 항목을 제외하면 나머지 8개 항목만으로는 일반적인 동물 관리 화면과 차이가 없음. 개발 우선순위 최상위 배치 권장
- 5~10번은 데모에 화면·개념이 이미 있으므로 설계 비용이 발생하지 않음

### 4-2. 제외

| 항목 | 제외 사유 |
| --- | --- |
| 임보자 체크인 전 과정 (요청·모바일 폼·검토·반영) | 인터뷰 신호 Tier 2. 알파 2차 1순위 후보 |
| 임보자 관리·배치 | 상동 |
| 외부 채널 게시 실행 | 대상 기관이 기존 게시 경로를 보유. 알파는 **상태 판정까지만 담당** |
| 신규 동물 등록 위저드 | 기존 CRM이 원장 시스템이므로 이중 입력이 발생 |
| 입양 문의·매칭·결과 기록 | 인터뷰 미검증 구간 |
| 기존 CRM API 양방향 연동 | 대상 CRM에 공개 API 부재. CSV 단방향 연동으로 충분 |

### 4-3. 명칭 참고

- 데모의 체크리스트 명칭은 `게시 요건`이나, 기관에 따라 게시 업무를 기존 CRM에서 수행하는 경우가 있음
- 해당 명칭을 **조직별 설정값으로 처리**할 것을 권장 (예: 입양 준비 요건)

## 5. 기간 추정

| 팀 규모 | 기능 개발 완료 | 알파 투입 가능 시점 |
| --- | --- | --- |
| 개발 2명 전담 | 4~6주 | **6~8주** |
| 개발 1명 전담 | 8~10주 | 10~12주 |

- 공수가 집중되는 구간은 3개: ① CSV 매핑(원본 데이터 상태에 좌우됨) ② 룰의 기관별 설정을 지원하기 위한 스키마 유연성 확보 ③ 자원봉사자 계정 체계
- **일정을 좌우하는 변수는 개발 범위가 아니라 전담 인력 규모임**

## 6. 성공 지표

Days of Care는 4주 단위 측정이 어려우므로 선행 지표로 대체한다.

| 지표 | 판정 의미 |
| --- | --- |
| **주간 검토 회의의 스프레드시트 미사용 여부** | **핵심 지표.** 스프레드시트 대체 가능성의 직접 확인 |
| 요건 해소 소요일 | pathway 정체 기간 단축 여부 |
| 대기열 처리율 | 실사용 여부 |
| 주간 활성 사용자 수 (담당자 외 직원·자원봉사자) | 조직 내 확산 여부 |

## 7. 착수 전제

| 전제 | 내용 |
| --- | --- |
| **CSV 샘플 확보** | 대상 CRM은 리포트 기반 추출 구조이며 추출 형식을 당사가 통제할 수 없음. **개발 착수 전 동물 개체 단위 리포트 CSV 샘플 1건 확보가 일정상 최대 변수임.** 미확보 시 반입 스펙 확정 불가 |
| 필드 설계 방침 | 필수 필드를 최소화하고 컬럼 매핑을 유연하게 설계 |
| 갱신 방식 | 수동 업로드를 전제. 알파 단계에서는 주 1회 갱신으로 충분 |

## 8. 결정 대기 사항

| # | 항목 | 판단 재료 |
| --- | --- | --- |
| 1 | **개발 전담 인력 규모** | 기간 추정을 좌우하는 변수 |
| 2 | 알파 범위 확정 | 4-1의 10개 항목 조정 여부. 특히 **임보자 체크인의 알파 포함 여부**. 인터뷰 신호는 Tier 2이나, 경쟁 제품의 동일 기능 출시 예정 시점과 겹침 (포지셔닝 문서 7장) |
| 3 | 자원봉사자 계정 처리 방식 | 정식 계정 발급 또는 읽기 전용 링크 제공 중 선택 |
| 4 | PoC·정규 계약 조건 | M2 Track 1과 연계. 벤치마크 사례는 포지셔닝 문서 참조 |

## 9. 유의 사항

- 현재 룰 계산 결과는 **고정 문자열이며 실계산은 미구현 상태**임 (4-1의 2번). 대외 커뮤니케이션에서 "룰이 판정한다"를 현재형으로 진술하지 않도록 유의
