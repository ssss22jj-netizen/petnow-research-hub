# Petify for Shelters 프리토타입 PRD v0.1

> 작성일: 2026년 8월 9일  
> 문서 상태: 제품 콘셉트 초안 · 펫나우팀 검토 전  
> 개발 대상: 클릭형 프리토타입  
> 제품 범위: 동물 Intake부터 준비 상태 관리와 사이트·외부 입양 채널 게시까지  
> 한 줄 정의: Petify for Shelters는 동물을 등록한 순간부터 필요한 정보와 임보 업데이트를 하나의 레코드에 모으고, 준비 상태를 판단해 게시까지 연결하는 Shelter CRM이다.

## 0. 제품 정의

Petify for Shelters는 현재 구현된 펫나우 CRM의 기능 범위를 재현하는 제품이 아니다. 시장에 제시할 새로운 Shelter CRM의 전체 경험을 검증하기 위해 설계하는 프리토타입이다. 따라서 현재 구현 여부나 기존 시스템 연동 여부에 제한받지 않고, 아래 흐름이 하나의 제품 안에서 완결되는 모습을 제시한다.

`Intake → 동물 레코드 생성 → 임보 배치 → 업데이트 수집·검토 → 준비 상태 판단 → 게시 프로필 완성 → 사이트·외부 채널 게시`

### 0.1 A·B·C의 제품 내 역할

| 기존 소재 | 제품에서 담당하는 역할 | PRD 반영 방식 |
| --- | --- | --- |
| A. 입양 준비 상태 판단 | 정보가 충분한 동물과 막힌 이유를 판단 | 제품의 핵심 의사결정 경험 |
| B. 임보 업데이트 독촉 해방 | 임보자에게 최신 건강·행동·사진 정보를 수집 | 준비 상태를 최신으로 유지하는 입력 흐름 |
| C. 인테이크 간소화 | 동물 레코드를 만들고 게시까지 이어지는 전체 흐름의 시작점 | 광고 소재에서는 제외했지만 제품의 필수 시작 단계로 유지 |

소재 C가 광고에서 제외됐다는 판단은 인테이크 기능을 제품에서 제거한다는 의미가 아니다. C는 독립적인 시장 진입 메시지로서 근거와 차별화가 부족했을 뿐, A와 B가 작동하려면 반드시 필요한 제품 기반이다.

### 0.2 제품 가치제안

| 사용자 | 가치제안 |
| --- | --- |
| 운영 책임자 | 전체 동물의 진행 상태와 게시 가능 여부를 한 화면에서 확인 |
| 임보·입양 코디네이터 | 임보자에게 반복 연락하지 않고 최신 정보를 받아 차단 항목과 다음 행동을 관리 |
| 임보자 | 계정이나 앱 설치 없이 링크에서 동물의 최신 상태와 사진 제출 |
| 게시 담당자 | 준비된 동물의 프로필을 다시 정리하지 않고 사이트와 외부 입양 채널에 게시 |

### 0.3 핵심 제품 약속

동물 정보는 Intake 때 한 번 입력하고 끝나는 것이 아니라, 케어·임보·검토 과정에서 계속 완성된다. Petify for Shelters는 이 정보를 하나의 동물 레코드에 축적하고, `무엇이 완료됐는지`, `무엇이 막혀 있는지`, `누가 다음 행동을 해야 하는지`를 보여준 뒤 준비가 끝나는 즉시 게시로 연결한다.

## 1. 프리토타입 목적

이번 프리토타입은 기술 구현 가능성을 검증하는 MVP가 아니다. 광고에서 제시한 페인포인트와 가치약속을 하나의 제품 경험으로 보여주고, 잠재 고객이 이 해결 방식에 구매 관심을 보이는지 확인하기 위한 프리토타입이다.

### 1.1 검증 질문

1. Intake부터 게시까지 하나의 동물 레코드로 이어지는 경험이 현재 업무보다 명확하게 낫다고 느끼는가?
2. 임보자 업데이트가 준비 상태 판단에 바로 연결되는 흐름에 비용을 지불할 가치가 있다고 느끼는가?
3. `Ready`, `Blocked`, `Needs review`와 차단 사유가 실제 의사결정에 충분한가?
4. 게시 전 필요한 정보·사진·서류가 한곳에 모이는 경험이 기존 CRM을 교체하거나 병행할 이유가 되는가?
5. 데모 이후 파일럿, 후속 미팅, 예산 담당자 연결 중 하나 이상의 행동을 보이는가?

### 1.2 프리토타입에서 검증하지 않는 항목

- 실제 데이터 저장 안정성과 시스템 성능
- 실제 SMS·이메일 발송 성공률
- Petfinder·Adopt a Pet API 연동 가능 여부
- 실제 홈페이지 게시 속도와 오류율
- 보안·권한·감사 기능의 운영 적합성
- 대량 데이터 마이그레이션과 기존 CRM 호환성
- 실제 사용자의 장기 반복 사용률

위 항목은 프리토타입 반응이 확인된 이후 기술 검증과 파일럿 PRD에서 다룬다.

## 3. 제품 범위

### 3.1 포함 범위

| 단계 | 제품이 제공할 경험 | 최종 산출 상태 |
| ---: | --- | --- |
| 1. Intake | 기본 정보·입소 맥락·사진으로 동물 레코드 생성 | `New intake` |
| 2. 레코드 구성 | 건강·행동·미디어·서류·공개 프로필을 한 레코드에 연결 | `In care` |
| 3. 임보 배치 | 동물과 임보자·담당자·기간 연결 | `In foster` |
| 4. 업데이트 수집 | 계정 없는 모바일 링크와 자동 리마인드로 최신 정보 수집 | `Update submitted` |
| 5. 업데이트 검토 | 기존 기록과 신규 제출을 비교해 승인·보완 요청 | `Needs review` 또는 `Approved` |
| 6. 준비 상태 판단 | 필수 항목·최신성·차단 사유·다음 행동 계산 | `Ready` 또는 `Blocked` |
| 7. 게시 프로필 완성 | 공개 설명·특성·사진·연락 정보를 미리보기 | `Ready to publish` |
| 8. 게시 | 쉘터 사이트와 외부 입양 채널에 발행·상태 확인 | `Published` |

### 3.2 제외 범위

프리토타입은 Intake부터 게시까지의 `pre-adoption CRM` 흐름에 집중한다. 다음 단계는 제품 내 메뉴나 향후 확장 안내로도 노출하지 않는다.

- 입양·임보 신청서 접수와 심사
- 레퍼런스 체크와 홈 체크
- 입양 계약·전자서명·결제
- 입양 완료 처리와 사후 오너 연결
- 기부·회계·직원 근태·봉사시간 관리
- 비문 인식 기반 개체 등록·식별
- 동물통제·면허·현장 출동 등 B2G 업무

## 4. 제품 설계 원칙

1. **동물 한 마리, 하나의 흐름:** Intake, 임보 업데이트, 준비 판단, 게시가 서로 다른 제품처럼 분리되지 않는다.
2. **정보 구조보다 다음 행동 우선:** 모든 데이터를 나열하기보다 지금 막힌 항목과 담당자가 해야 할 행동을 먼저 보여준다.
3. **제출과 승인 분리:** 임보자의 제출은 바로 공식 기록을 덮어쓰지 않고 운영자 검토를 거친다.
4. **준비 상태의 근거 표시:** 상태 라벨뿐 아니라 판단에 사용한 항목, 최신 확인일, 차단 사유를 함께 보여준다.
5. **점진적 정보 완성:** Intake 시점에 모든 정보를 요구하지 않고, 이후 업무에서 레코드가 완성되게 한다.
6. **계정 없는 외부 참여:** 임보자는 앱 설치나 계정 생성 없이 요청받은 과업만 완료한다.
7. **예외 중심 운영:** 정상 상태보다 미응답, 변화, 오래된 정보, 검토 필요 항목을 우선 표시한다.
8. **게시 전 단일 검토:** 공개 프로필을 한 번 확인한 뒤 선택한 채널에 보낸다.

## 6. 상태 모델

### 6.1 동물 진행 단계

| 단계 | 의미 | 다음 전환 조건 |
| --- | --- | --- |
| New intake | 동물 레코드가 생성된 직후 | 기본 Intake 저장 |
| In care | 케어·임보·준비 정보가 쌓이는 중 | 임보 배치 또는 준비 항목 처리 시작 |
| Needs review | 신규 제출이나 담당자 판단이 대기 중 | 운영자 승인·보완 요청 완료 |
| Ready to publish | 조직이 정한 필수 준비 항목 충족 | 공개 프로필 최종 검토 |
| Published | 한 개 이상의 선택 채널에 게시 완료 | 게시 취소·정보 수정·재검토 발생 |

### 6.2 준비 상태

| 상태 | 조건 | 화면 표현 |
| --- | --- | --- |
| Ready | 모든 필수 항목이 완료되고 최신이며 검토 대기 없음 | 준비 완료 시점, 완료 근거, `Preview & publish` |
| Blocked | 필수 항목이 누락·만료·보완 요청 상태 | 주요 차단 사유, 담당자, 다음 행동, 기한 |
| Needs review | 준비 상태에 영향을 주는 제출이 검토 중 | 제출자, 제출 시점, 주의 항목, `Review update` |

`Ready`는 의료·법적 판단을 제품이 대신한다는 의미가 아니다. 조직이 설정한 게시 준비 체크리스트가 충족됐다는 운영 상태다.

### 6.3 업데이트 상태

| 요청 상태 | 제출 상태 |
| --- | --- |
| Scheduled, Sent, Opened, In progress, Submitted, Overdue, Expired | Draft, Submitted, In review, Approved, Partially approved, Changes requested, Rejected |

### 6.4 게시 상태

| 상태 | 의미 |
| --- | --- |
| Draft | 공개 정보가 작성 중 |
| Blocked | 게시 필수 정보 또는 승인이 누락 |
| Ready | 미리보기와 게시 조건 충족 |
| Publishing | 선택 채널에 전송 중 |
| Published | 채널에서 게시 완료 |
| Failed | 채널 전송 실패. 원인과 재시도 행동 표시 |

## 7. 핵심 사용자 흐름

### 7.1 End-to-end 데모 시나리오

하나의 동물 `Milo`가 Intake부터 게시까지 이동하는 과정을 기본 데모 시나리오로 사용한다.

| 순서 | 사용자 행동 | 시스템 반응 | 보여줘야 할 가치 |
| ---: | --- | --- | --- |
| 1 | `Add animal`에서 Milo의 기본 정보·입소 정보·사진 저장 | 동물 레코드와 준비 체크리스트 생성 | 모든 정보를 먼저 채우지 않고 업무 시작 |
| 2 | 임보자 Jamie와 배치 기간 연결 | Milo 상태가 `In foster`로 변경되고 업데이트 일정 생성 | 동물·사람·업무 일정 연결 |
| 3 | 주간 업데이트 요청 발송 | Jamie에게 계정 없는 모바일 링크 발송 | 반복 연락을 구조화된 요청으로 대체 |
| 4 | Jamie가 행동 변화와 사진 제출 | 제출이 `Needs review`로 들어오고 변화 항목 강조 | 흩어진 메시지 대신 한 번에 수집 |
| 5 | 코디네이터가 기존 행동 기록과 비교해 승인 | 행동 항목 최신화, 제출 이력 보존 | 안전한 정보 반영 |
| 6 | 시스템이 준비 상태 다시 계산 | 유일한 차단 사유가 해소돼 `Ready`로 변경 | 사람에게 묻지 않고 준비 여부 판단 |
| 7 | 게시 담당자가 공개 프로필 미리보기 | 내부 메모를 제외한 공개 정보·사진 표시 | 재입력 없이 게시 정보 완성 |
| 8 | 사이트·Petfinder·Adopt a Pet 선택 후 게시 | 채널별 `Published` 상태와 게시 시각 표시 | Intake부터 게시까지 하나의 흐름 완결 |

### 7.2 소재별 데모 진입점

| 광고 소재 | 데모 시작 화면 | 이후 연결 |
| --- | --- | --- |
| A. 입양 준비 상태 판단 | Animals의 Ready·Blocked 목록 | Blocked 동물 상세 → 업데이트 검토 → Ready → 게시 |
| B. 임보 업데이트 독촉 해방 | Updates의 미응답·신규 제출 현황 | 요청 발송 → 임보자 제출 → 승인 → Ready → 게시 |

두 소재는 다른 제품을 보여주지 않는다. 시작 화면만 다르고 동일한 Milo 레코드와 Intake-to-publish 흐름으로 합류한다.

## 10. 프리토타입 상호작용 규칙

프리토타입은 실제 외부 시스템과 연결하지 않지만, 사용자의 행동과 제품 결과가 인과적으로 이어져야 한다.

| 사용자 행동 | 화면 상태 변화 |
| --- | --- |
| Intake 저장 | 새 동물이 Animals 목록에 추가되고 `Blocked` 체크리스트 생성 |
| 임보 배치 저장 | 임보자·담당자·업데이트 일정이 동물 상세에 반영 |
| 업데이트 요청 발송 | 요청 상태가 `Sent`로 변경되고 Foster Mobile Form으로 이동 가능 |
| 임보자 제출 | Updates에 `Needs review` 항목 생성 |
| 업데이트 승인 | 관련 준비 항목이 Complete로 변경되고 상태 재계산 |
| 마지막 차단 항목 해결 | 동물이 `Ready to publish`로 변경되고 게시 행동 활성화 |
| 게시 실행 | 선택 채널이 Publishing 후 Published로 변경되고 공개 링크 표시 |
| 게시 실패 선택 | 한 채널만 Failed로 남고 원인·재시도 버튼 표시 |

페이지를 이동해도 동일 데모 세션에서는 변경된 상태가 유지돼야 한다. `Reset demo`를 실행하면 최초 시나리오로 돌아간다.

## 12. UX Writing 기준

| 원칙 | 적용 예시 |
| --- | --- |
| 상태와 이유를 함께 표현 | `Blocked · Behavior update is 18 days old` |
| 다음 행동을 동사로 표시 | `Request update`, `Review submission`, `Fix & retry` |
| 자동 판단처럼 과장하지 않음 | `Ready based on your organization’s checklist` |
| 임보자에게 내부 용어를 요구하지 않음 | `How is Milo doing?` 후 변화가 있을 때 상세 질문 |
| 제출·승인 차이를 명확히 표현 | `Submitted for review`, `Approved and added to Milo’s record` |
| 게시 결과를 채널별로 표시 | `Petfinder · Published 10:42 AM`, `Adopt a Pet · Failed` |

## 13. 프리토타입 완료 조건

### 13.1 화면 완결성

- Dashboard, Animals, Updates, Fosters, Publishing, Settings 메뉴 이동 가능
- New Intake부터 채널 게시까지 Milo 또는 Coco 기준 End-to-end 흐름 완주 가능
- A 소재 진입 화면과 B 소재 진입 화면이 동일 제품 상태로 연결
- 운영자 화면과 임보자 모바일 화면의 역할 차이가 명확함
- 주요 버튼이 실제 화면 상태를 변경하며 막힌 링크나 무반응 버튼이 없음
- Ready·Blocked·Needs review의 조건과 상태 변화가 데모 내에서 일관됨
- 공개 프로필에서 내부 메모·임보자 연락처가 노출되지 않음
- 데스크톱 운영 화면과 모바일 임보자 화면을 데모할 수 있음

### 13.2 메시지 완결성

- Intake 때 저장한 동물 정보가 이후 모든 화면에서 동일하게 유지
- 임보 업데이트가 별도 기능으로 끝나지 않고 준비 상태 변화로 연결
- 준비 상태가 별도 대시보드에서 끝나지 않고 게시 행동으로 연결
- 게시 기능이 단일 성공 화면이 아니라 채널별 준비·성공·실패 상태를 보여줌
- 기존 구현 기능이 아니라 새 제품 콘셉트라는 사실은 데모 초대·진행 안내에서 명확히 고지

## 14. 데모 반응 판정

프리토타입의 목표는 기능 선호 조사보다 가치약속에 대한 buying 반응을 확인하는 것이다.

| 신호 | 확인할 행동·발언 | 해석 |
| --- | --- | --- |
| 문제 공감 | 현재도 사람에게 물어보거나 여러 도구를 확인한다고 설명 | 문제 가설 지지 |
| 해결 매력 | 업데이트 승인 후 Ready·게시로 이어지는 흐름을 현재 방식보다 낫다고 평가 | 통합 제품 흐름 지지 |
| 데이터 요구 | 실제 동물·임보자·체크리스트를 넣어 보고 싶다고 요청 | 파일럿 관심 신호 |
| 전환 검토 | 현재 CRM의 어떤 기능을 대체·병행할지 구체적으로 질문 | 도입 검토 신호 |
| 구매 행동 | 후속 미팅, 파일럿, 예산 담당자 연결, 가격 논의에 동의 | 제품 가설 진전 |
| 반대 신호 | 업데이트·준비·게시가 이미 현재 CRM에서 충분히 완결된다고 설명 | 차별화 가설 약화 |
| 범위 반대 | 신청·계약·결제 없이는 CRM 전환이 불가능하다고 설명 | 제품 범위 확장 여부 검토 |
