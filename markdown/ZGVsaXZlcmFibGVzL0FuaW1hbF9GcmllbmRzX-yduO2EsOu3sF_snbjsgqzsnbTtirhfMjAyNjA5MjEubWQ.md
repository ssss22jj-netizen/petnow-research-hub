# Animal Friends 인터뷰 인사이트

> **Animal Friends의 의료팀에는 임보자의 의료 관련 요청을 유형별로 나누고, 담당자와 처리 상태를 팀 전체가 확인하는 기능이 잘 맞는다.** 의료팀은 Shelterluv를 공식 기록으로 유지하려 한다. 제품을 긍정적으로 평가했지만, 파일럿에 참여할지와 비용을 지불할 의향이 있는지는 아직 확인되지 않았다.

## 2. 현재 업무 방식

| 현재 업무 | 확인된 문제 |
| --- | --- |
| 공용 의료 이메일 수신 | 임보 업데이트·진료 예약·약 추가 공급 요청(리필)·의료 질문·응급병원 알림·검사실 결과가 의료팀의 공용 받은편지함에 섞여 들어온다. 주말 이틀 뒤 약 170개 이메일이 쌓인 사례가 있었다. |
| 최대 약 10명 동시 수신 | 의료팀 직원들이 같은 이메일을 함께 받는다. 요청을 받은 직원이 휴무여도 다른 직원이 확인하고 대응할 수 있도록 하기 위해서다. |
| 이메일로 담당·완료 확인 | 직원들은 누가 요청을 처리했고 무엇이 남았는지 확인하려고 이메일을 다시 읽거나 추가로 회신해야 한다. |
| 임보자 응답을 기록으로 정리 | 임보자와는 이메일로 소통하고 공식 의료 기록은 Shelterluv에 보관하므로, 직원이 이메일에서 받은 정보를 Shelterluv 기록으로 옮겨야 한다. |

## 3. 검증 대상

소재 B는 임보자 업데이트를 수집하고 반복해서 확인하는 업무를 줄일 수 있다는 가설을 검증한다. 이 콜에서는 업데이트 수집에 더해 의료 요청을 유형별로 나누고 처리 상태를 팀에서 공유하는 기능까지 필요한 것으로 나타났다.

| 검증 대상 | 결과 |
| --- | --- |
| 임보자 소통이 실제 반복 업무인가 | Cara는 공용 의료 이메일에 임보 요청·검사실·응급병원 연락이 섞여 들어오며, 주말 이틀 뒤 약 170개가 쌓인 사례를 설명했다. |
| 업데이트를 모으면 업무가 줄어드는가 | 업데이트를 모은 뒤에도 누가 요청을 처리했고 무엇이 남았는지 확인할 수 있어야 한다. |
| 기존 CRM을 교체해야 하는가 | 의료팀은 Shelterluv를 공식 의료 기록으로 유지하면서 Petify로 임보 요청 처리를 보완하는 방식에 긍정적으로 반응했다. |
| 앱·로그인 없는 응답이 선택 이유인가 | Cara가 앱 설치나 로그인 없이 응답할 수 있다는 점을 강한 선택 이유로 직접 강조하지는 않았다. 실제 선택에 얼마나 중요한지는 추가로 확인해야 한다. |

> “we'll be able to see, hey, so and so took care of this”

Cara가 요청을 처리한 사람을 팀에서 확인할 수 있다는 가치를 설명한 발언이다(정리본 §6). 의료팀의 업무를 줄이려면 연락을 자동으로 보내는 데 더해, 요청을 받은 뒤 누가 담당하고 처리를 마쳤는지까지 확인할 수 있어야 한다.

## 5. 발언 뒤에 있는 것

- **업무 문제의 심각도는 매우 강함으로 평가한다.** [해석·L2] 실무자가 이메일 업무량과 요청의 담당자·완료 여부를 확인하는 어려움을 구체적으로 설명했다. 170개는 특정 주말 뒤에 쌓인 이메일 수이며, 일평균으로 환산하지 않는다.
- **요청마다 담당자를 정하되 팀 전체가 처리 상태를 볼 수 있어야 한다.** [해석·L2] 의료팀 직원 최대 약 10명이 같은 이메일을 받는 이유는 누군가 휴무여도 다른 직원이 요청에 대응하기 위해서다. 요청을 배정받은 직원만 내용을 볼 수 있다면, 그 직원이 자리를 비웠을 때 다른 직원이 대신 대응하기 어려워질 수 있다.
- **의료 요청 처리 기능은 이 팀의 업무에 잘 맞는다.** [해석·L2] Cara가 다음 진료 예약과 약 리필을 구체적인 활용 사례로 제시했다는 점이 근거다. 다음 검사·백신·리필 예정일을 중심으로 보여주는 화면은 이 문서에서 제안하는 제품 가설이며, 실제로 필요한지는 후속 검토에서 확인해야 한다.
- **현재 자료로 유료 전환 가능성을 판정할 수 없다.** [해석·L2] 현재 업무량이 많아 업무를 줄일 여지는 있지만, 비용을 지불할 의향이나 예산 승인을 확인한 것은 아니다. 파일럿에서 시험할 범위와 실제 구매 조건을 따로 확인해야 한다.

## 6. 언급된 기능 요청

| 기능 요청 | 발언 맥락 |
| --- | --- |
| 임보 요청을 한곳에서 분리 처리 | 검사실·응급병원 연락과 섞여 들어오는 임보 요청을 공용 의료 이메일에서 분리해 따로 보고 싶다고 설명했다. |
| 약 리필·의료 질문별 분류 | 요청을 세부 유형별로 나눌 수 있다면 좋겠다고 반응했다. |
| 담당자와 처리 상태 확인 | 누가 요청을 처리했고 무엇이 남았는지 팀에서 확인할 수 있다는 가치를 직접 설명했다. |
| 다음 진료 예약 요청 | 임보자에게 다음 검진을 예약하도록 요청하는 데에도 Petify를 사용할 수 있는지 질문했다. |
| 약 리필 요청 처리 | 임보 동물의 건강 상태를 정기적으로 확인하는 체크인에 약 리필 요청도 포함하는 활용 사례를 제시했다. |
| Shelterluv 연결 | Shelterluv를 공식 의료 기록으로 유지하면서, 직원이 검토한 임보자 응답을 Shelterluv에 반영한다는 설명에 긍정적으로 반응했다. |

## 7. 남은 것

1. **의료팀의 실제 요청 처리 과정을 확인한다.** 사례 한 건을 기준으로 요청을 어떻게 분류하고 담당자를 정하는지, 담당자가 없을 때 누가 이어받는지, 언제 처리가 완료됐다고 판단하는지 확인한다.
2. **Shelterluv와 연동할 수 있는 범위를 검증한다.** 동물과 임보 배정 정보를 가져올 수 있는지, 직원이 검토한 결과를 반영할 수 있는지, 동물 상태가 바뀌면 어떤 정보까지 함께 갱신할 수 있는지 확인한다.
3. **파일럿을 검토할 사람과 참여 조건을 확인한다.** Cara·Kathy와 내부 결정권자가 참여할지, 유료 전환에 필요한 예산과 승인 절차는 무엇인지 확인한다. 파일럿 참여 여부는 별도로 합의해야 한다.

업무가 개선됐는지 확인할 지표 후보로 **임보 요청을 받은 뒤 처리를 마칠 때까지 걸린 시간, 오래 처리되지 않은 요청 수, 담당자나 완료 여부를 확인하려고 추가로 연락한 횟수, 검토한 결과를 Shelterluv 기록에 반영할 때까지 걸린 시간**을 제안한다. 이메일 수가 줄었는지만으로 업무 개선을 판단하지 않는다.

## 부록

입양 게시와 전체 의료 CRM은 이번 콜에서 핵심 요구로 다뤄지지 않았다. Community Support 부서는 Dubert를 사용한다고 설명했으며 의료팀 사용 방식과는 구분된다.
