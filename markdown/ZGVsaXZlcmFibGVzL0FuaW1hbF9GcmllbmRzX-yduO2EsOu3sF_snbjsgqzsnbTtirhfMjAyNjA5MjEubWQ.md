# Animal Friends 인터뷰 인사이트

> **의료 임보 요청을 업무 유형별로 나누고, 담당자와 처리 상태를 팀 전체가 확인하는 기능에 적합성이 높다.** Shelterluv는 공식 기록으로 유지한다. 제품 검토 반응은 긍정적이지만 파일럿 참여와 지불 의향은 아직 확인되지 않았다.

## 3. 검증 대상

소재 B는 임보자 업데이트 수집과 반복 확인을 줄이는 가설이다. 이 콜에서는 의료 요청의 분류와 처리 상태 공유까지 필요한 것으로 나타났다.

| 검증 대상 | 결과 |
| --- | --- |
| 임보자 소통이 실제 반복 업무인가 | 공용 의료 이메일에 임보 요청·검사실·응급병원 연락이 섞이며, 주말 이틀 뒤 약 170개가 누적된 사례 설명 |
| 업데이트를 모으면 업무가 줄어드는가 | 수집 이후 누가 처리했고 무엇이 남았는지 확인하는 기능까지 필요 |
| 기존 CRM을 교체해야 하는가 | Shelterluv를 공식 의료 기록으로 유지하면서 임보 요청 처리를 보완하는 방식에 긍정 |
| 앱·로그인 없는 응답이 선택 이유인가 | Cara가 이를 강한 선택 이유로 직접 강조하지는 않아 추가 검증 필요 |

> “we'll be able to see, hey, so and so took care of this”

Cara, 처리한 사람을 팀에서 확인할 수 있다는 가치를 설명한 발언(정리본 §6). 자동 연락만으로는 충분하지 않고, 요청을 받은 뒤의 담당·완료 확인까지 연결돼야 한다.

## 5. 발언 뒤에 있는 것

- **통증 강도는 매우 강함으로 판단한다.** [해석·L2] 업무량 수치와 담당·완료 확인의 어려움을 실무자가 설명했다. 170개는 특정 주말 뒤 누적량이며 일평균으로 환산하지 않는다.
- **담당자 지정과 팀 가시성이 함께 필요하다.** [해석·L2] 최대 약 10명 동시 수신은 휴무 중에도 대응을 이어가기 위한 운영 방식이다. 개인 배정만 적용하면 현재 확보한 업무 연속성을 잃을 수 있다.
- **의료 요청 처리 기능에 적합성이 높다.** [해석·L2] 다음 진료와 약 리필까지 활용을 확장한 반응이 근거다. 다음 검사·백신·리필 예정일 중심 화면은 후속으로 검증할 제품 가설이다.
- **현재 자료로 유료 전환 가능성을 판정할 수 없다.** [해석·L2] 큰 업무량은 절감 여지를 뜻하지만 지불 의향이나 예산 승인을 뜻하지 않는다. 파일럿 범위와 구매 조건을 따로 확인해야 한다.

## 6. 언급된 기능 요청

| 기능 요청 | 발언 맥락 |
| --- | --- |
| 임보 요청을 한곳에서 분리 처리 | 검사실·응급병원 연락과 섞인 공용 의료 이메일에서 임보 요청을 따로 보고 싶다고 설명 |
| 약 리필·의료 질문별 분류 | 요청을 세부 유형별로 나눌 수 있다면 좋겠다고 반응 |
| 담당자와 처리 상태 확인 | 누가 처리했고 무엇이 남았는지 팀에서 확인하는 가치를 직접 설명 |
| 다음 진료 예약 요청 | 다음 검진을 잡도록 임보자에게 요청하는 흐름에 사용 가능한지 질문 |
| 약 리필 요청 처리 | 체크인 구조에 약 리필 요청을 넣는 활용 사례 제시 |
| Shelterluv 연결 | 공식 의료 기록을 유지하면서 검토된 결과를 연결하는 설명에 긍정 |

## 7. 남은 것

1. **의료팀의 실제 요청 처리 과정 확인.** 요청 분류, 담당자 지정, 부재 시 인계, 완료 판단을 사례 한 건으로 확인한다.
2. **Shelterluv 연동 검증.** 동물·임보 배정 정보 가져오기, 검토 결과 반영, 동물 상태 변경 시 동기화 범위를 확인한다.
3. **파일럿 검토 주체와 조건 확인.** Cara·Kathy와 내부 결정권자의 참여 여부, 유료 전환 시 예산·승인 절차를 확인한다. 파일럿 참여는 별도 합의가 필요하다.

성과 지표 후보는 **요청 처리시간, 장기 미처리 요청 수, 담당·완료 확인을 위한 추가 연락 수, Shelterluv 반영까지 걸린 시간**이다. 이메일 감소만으로 업무 개선을 판단하지 않는다.
