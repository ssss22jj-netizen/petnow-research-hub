# 경쟁사 데모 제품 UI·UX 통합분석

> 기능 범위는 제품별로 유사하지만, 사용성 차이는 기능 수보다 과업 연결 방식에서 발생한다. Petstablished는 임보자 지정과 동물 상태 변경을 한 동작으로 연결했지만, 실제 운영 계정에서도 초기 등록·의료·입양 정보가 여러 화면과 설정으로 분산돼 있다.

- 분석 대상: Shelterluv, Pawlytics, Animal Shelter Manager, PawPlacer, Petstablished
- 별도 분석 대상: Chameleon/CMS
- 분석 방식: 동일 사용자 역할·과업 기반 전문가 워크스루 및 사용자 리뷰 교차검증
- 기준일: 2026.07.29

## 핵심 판단

| 항목 | 현재 결과 |
| --- | --- |
| 분석 완료 | Shelterluv 운영자 계정, Pawlytics 정식 운영 계정, Animal Shelter Manager·PawPlacer 워크스루, Petstablished 실제 운영 계정 37개 화면·테스트 레코드 검증 |

| 기능 범위 우위 | Animal Shelter Manager. 의료·행동·임보·입양 기능은 깊지만 고밀도 데스크톱 UI와 학습 부담 확인 |

## 이 문서 사용법

- **제품 간 빠른 비교**: 바로 아래 정량 비교 표 → 섹션 6 교차 비교 순으로 읽기
- **특정 제품 상세**: Shelterluv는 섹션 3, Pawlytics·ASM·PawPlacer는 섹션 4, Petstablished는 섹션 5
- **펫나우 설계 기준**: 섹션 7 설계 시사점으로 바로 이동
- **분석 신뢰도**: 섹션 8 공통 분석 한계 + 각 섹션 분석 한계 참조

## 3. Shelterluv 무료 체험 워크스루

- 계정: 무료 체험 계정 `DEMO_2850`
- 테스트 데이터: 가상 데이터만 사용
- 현재 상태: T1 데스크톱 완료, T2 운영자 계정 대체 검증 완료·임보자 직접 입력 미검증, T3 운영자 결제 링크 발송 완료·입양자 계약 및 결제 미검증

### 3.1 현재 결론

| 구분 | 결과 | 핵심 관찰 |
| --- | --- | --- |
| T1 신규 동물 등록 및 임보자 배치 | 완료 | 동물 등록과 임보 배치가 별도 이벤트로 분리. 종·견종 선택 후 앞선 입력값이 초기화되어 재입력 발생 |
| T2 임보자의 사진·투약·행동 기록 입력 및 담당자 확인 | 부분 완료 | 운영자 계정에서 의료·행동 메모 입력과 담당자 확인 구조 확인. 임보자 계정의 직접 입력 흐름은 미검증. Daily Observations는 종별 유형 미설정으로 비활성. 사진 업로드는 정상 동작 가정에 따라 결함 판정에서 제외 |
| T3 입양 신청부터 계약·결제·상태 변경 | 부분 완료 | Jamie Lee 생성, Milo 선택, 입양 정보 입력 및 Shelterpay $200 결제 링크 발송 완료. 입양자용 모바일 화면의 계약·서명·결제와 결제 후 동물 상태 변경은 미검증 |

### 3.2 과업별 측정

| 과업 | 완료시간 | 화면 전환 수 | 입력 필드 수 | 중복 입력 | 막힌 지점 | 모바일 완결성 | 리뷰 불만 재현 |
| --- | ---: | ---: | ---: | ---: | --- | --- | --- |
| T1 신규 동물 등록 및 임보자 배치 | 8분 44초 | 16회 | 약 37개 | 8회 이상 | 종·견종 선택 후 일정·메모·연령 초기화, 제출 오류 후 재입력 | 운영자용 모바일 양식 접근 가능. 모바일에서 저장까지 재수행하지 않아 완결성은 추정 | 입력 필드·단계 과다 부분 재현, 신규 발견: 동적 필드 초기화 |

> 입력 필드 수는 사용자가 직접 값을 입력하거나 선택한 항목 기준. T1은 재입력한 항목을 중복 입력에 별도 계상한 잠정치.

### 3.3 주요 관찰

| 관찰 사실 | 과업 영향 | 판정 |
| --- | --- | --- |
| Stray Intake가 발견자 사람 기록 생성에서 시작 | 동물 등록 전에 사람의 주소·전화·이메일 9개 항목 입력 필요 | 단계 증가 |

- **상태 변경 안전장치**: 입양 완료 동물은 일반 상태 선택으로 수정할 수 없고 `Undo Adoption` 또는 `Return Pet` 절차를 요구
- **정보 밀도 부담**: 동물 상세 화면에 기본 정보, 이미지, 영상, 특성, 행동, 위치, 입소·결과, 의료, 문서, 마이크로칩, 라이선스가 한 편집 화면에 연속 배치
- **결제 설정 의존성**: 입양비 결제 링크 생성은 은행 계좌 설정이 선행돼야 하며, 현재 계정에서는 해당 단계에서 차단
- **목록 관리 일관성**: 검색·정렬·필터·일괄 작업·보기 방식이 여러 화면에 반복 적용돼 숙련자의 대량 운영을 지원
- **설정 장문화**: Pet Defaults는 모바일 약 10,034px, 가시 컨트롤 136개로 초기 설정과 변경 영향 파악 부담이 큼
- **저장 동작 불일치**: `Next`가 레코드를 즉시 생성하고, 동일한 `Save changes` 문구의 상단 버튼은 변경값을 저장하지 못했으나 하단 버튼은 정상 저장
- **데이터 무결성 위험**: 품종 자동완성에서 `Labrador Retriever` 입력 후 Enter 시 첫 후보 `Affenpinscher`가 저장되는 현상 재현
- **삭제·복구 구조**: 브라우저 기본 확인창 후 소프트 삭제되며 삭제 항목 검색과 `Restore Pet` 메뉴 제공. 실제 복구 실행은 미검증
- **모바일 과업별 격차**: 기본 페이지는 화면 폭에 맞지만 의료 기록 모달의 제목과 `Create Record`가 오른쪽에서 잘림

### 6.1 데이터 계층과 업무 계층의 불일치 — 업무 플로우 인사이트 1 검증

업무 플로우 딥리서치 인사이트 1(제품의 기본 단위는 단계가 아니라 동물·사건·상태 변화다)을 5개 제품 데모에서 확인한 결과. 근거 수준: 데모 직접 관찰과 리뷰 분석 종합이며, 각 제품의 내부 데이터 구조는 화면·공개자료 기반 추정.

이 원칙은 업계 데이터 표준이라 경쟁 제품의 저장 구조에는 이미 반영돼 있다. ASM은 동물 상세에서 입소·결과를 분리 관리하고 입양 완료 동물의 상태 수정에 `Undo Adoption`·`Return Pet` 절차를 강제하며, Shelterluv는 입양 1건당 $2의 사건 단위 과금을 쓴다. 격차는 이 구조를 현장 업무 흐름으로 꺼내주는 화면의 부재에서 발생하며, 세 가지 형태로 나타난다.

1. **레코드 편집 화면으로 회귀한다.** 데이터는 사건 단위로 저장되지만, 사용자가 만나는 것은 동물 파일 하나를 열어서 고치는 경험이다. Shelterluv 등록 양식은 필드 37개(SL-T1-01), ASM은 기본 정보·행동·위치·입소 결과·의료·문서 등 12개 섹션을 한 편집 화면에 연속 배치한다.
2. **다차원 상태를 분리하지 않는다.** 법적·의료·행동·물리 위치·예상 결과·입양 공개 상태는 각각 따로 움직이는데, 경쟁 제품은 대표 상태 필드와 위치 정도만 두고 차원 간 동기화를 강제하지 않는다. 리뷰 반복 병목 1위인 위치·상태 불일치가 그 결과다. 예외적으로 PawPlacer는 임보 배치 시 상태·위치·임보자·시작일을 한 화면에서 함께 저장한다(PP-T1-04).
3. **상태 변화가 다음 행동을 만들지 않는다.** 무엇이 이 동물의 다음 이동을 막고 있는가(차단 사유·담당·기한)를 보여주는 화면은 검증한 어느 제품에도 없다. 현장은 이 공백을 Population Rounds 회의로 매일 수동 보완한다. 부분 채택 사례로 Petstablished는 임보자 지정 시 동물 상태가 `Fostered`로 함께 바뀐다는 것을 실행 전에 안내한다(PS-T1-01, PS-T3-01).

**경쟁 비교 주장 프레임**: "경쟁사에 없는 데이터 구조"가 아니라 "같은 데이터를 상태 변화 중심 업무 화면으로 꺼내주는 제품의 부재"로 세워야 방어 가능하다.

## 7. 펫나우 제품 설계 시사점

리뷰에서 반복된 기록 불일치·외부 문서 병행·전환 장벽과 데모에서 확인한 화면 마찰을 함께 반영한 결정 기준. `[상위 판단 연결]`은 앞의 제품 판단에서 도출한 기준이고, `[데모 화면 관찰]`은 특정 화면에서 직접 확인한 세부 개선점임.

### 신규 동물 등록

- `[상위 판단 ⑤ 연결]` **조건 필드가 바뀌어도 기존 입력값을 지우지 않는다.** 종·견종 선택으로 새 필드가 나타나더라도 이미 입력한 이름·나이·메모는 유지된다. ← Shelterluv 종 선택 후 8회 이상 재입력 발생
- `[데모 화면 관찰]` **동물 기본 정보가 먼저, 발견자·이전 보호자는 이후 단계로 분리한다.** 이름·종·나이·성별 등록 후 발견자 정보는 '나중에 추가'로. ← Shelterluv Stray Intake 발견자 9개 항목 선행
- `[상위 판단 ① 연결]` **필수 입력 항목 목표는 11개 이하다.** 나머지는 저장 후 추가 입력으로 유도. ← ASM 11개 필드 T1 2분 43초 완료 vs Shelterluv 37개
- `[상위 판단 ⑤ 연결]` **저장된 값을 화면에서 바로 확인할 수 있다.** 입력값과 저장값이 다르면 즉시 표시. ← Shelterluv "2세" 입력 → "0Y/5M/0D" 저장

### 임보 배치

- `[상위 판단 ④ 연결]` **임보 배치를 확정할 때 관련 정보를 함께 저장한다.** 동물 상태·현재 위치·임보자·배치 시작일·담당 코디네이터·다음 확인 업무를 한 번에 반영. 별도 단계 때문에 실제 누락이 발생한 것은 이번 데모에서 확인하지 않았으며, 리뷰의 기록 불일치 사례를 근거로 검증 필요성을 도출함. ← PawPlacer 임보 배치 화면
- `[데모 화면 관찰]` **상태 변경의 영향 범위를 실행 전에 문장으로 안내한다.** 임보자를 지정하면 동물 상태도 `Fostered`로 변경된다는 결과를 버튼 실행 전에 표시. ← Petstablished 임보자 지정 화면
- `[상위 판단 ② 연결]` **임보 중인 동물도 일상 관찰 기록이 초기 설정 없이 기본으로 활성화된다.** ← Shelterluv Daily Observations 선행 설정 필요, ASM 임보 동물 Daily Obs 제외

### 저장·오류 처리

- `[상위 판단 ⑤ 연결]` **저장 버튼이 있는 모든 화면에서 결과를 명시한다: 저장 중(스피너) / 저장 완료(타임스탬프) / 저장 실패(이유 + 재시도 버튼).**
- `[상위 판단 ⑤ 연결]` **저장에 실패하거나 과업을 중단해도 입력값과 진행 상태를 유지한다.** 재입력 없이 재시도하고 변경 전후 비교와 이전 상태 복원이 가능해야 함.

### 투약·행동 기록

- `[데모 화면 관찰]` **투약 빈도는 선택지로 입력한다: "하루 1회" "하루 2회" "격일" "필요시" 등.** 수량 × 단위 조합 방식은 쓰지 않는다. ← PawPlacer 빈도 표현 모호
- `[상위 판단 ② 연결]` **임보자가 직접 기록을 남길 수 있는 흐름을 만든다.** 코디네이터가 대신 입력하는 구조에 의존하지 않는다.

### 입양·결제

- `[데모 화면 관찰]` **입양 처리 시작 전, 미완료 항목을 먼저 보여준다:** 마이크로칩 미등록, 중성화 미완료, 광견병 접종 기한 경과 등. ← Shelterluv Missing Microchip 경고
- `[데모 화면 관찰]` **결제·계약·상태 변경 같은 되돌리기 어려운 동작 전에 변경 내용과 취소 가능 여부를 먼저 보여준다.** ← ASM·PawPlacer 최종 실행 전 화면
- `[데모 화면 관찰]` **결제 링크 발송 후에도 동물 상태를 바로 '입양 완료'로 바꾸지 않는다.** 결제·계약 완료 확인 후 상태를 변경. ← Shelterluv 결제 대기 상태
- `[데모 화면 관찰]` **신청 상태와 조직별 진행 단계를 분리한다.** 공통 상태는 집계 기준으로 유지하고, 연락·인터뷰·레퍼런스 확인 등 조직별 단계는 별도 진행 상태로 관리. ← Petstablished 신청 관리 화면

### 모바일

- `[상위 판단 ③ 연결]` **화면 적응성과 역할별 과업 완결성을 분리해 검증한다.** 화면 적응성은 단일 열 재배치·터치 영역·가로 스크롤 여부, 역할별 과업 완결성은 임보자 입력→운영자 확인→동물 상태·후속 업무 반영 여부를 뜻함.
- `[상위 판단 ③ 연결]` **목록 화면에서 표 대신 카드를 쓴다.** 가로 스크롤을 없애고 핵심 행동 버튼은 하단에 고정. ← PawPlacer 모바일 단일 열 카드
- `[데모 화면 관찰]` **기본 페이지의 반응형 처리와 모달의 과업 완결성을 따로 검증한다.** Petstablished 37개 기본 페이지는 가로 오버플로가 없지만 의료 기록 모달의 핵심 조작부가 잘리고 Pet Defaults는 10,034px임. 필드 단계화·모달 적응·저장 완결성을 함께 검증.

### 도입·연동

- `[상위 판단 ① 연결]` **기존 CRM을 즉시 교체하지 않아도 사용할 수 있어야 한다.** 초기에는 운영자가 변경 내용을 확인한 뒤 내보내고, 검증된 항목부터 동기화. ← 리뷰에서 데이터 이전·교육·외부 연동의 전환 장벽 확인

## 8. 공통 분석 한계

- 실제 사용자가 아닌 전문가 워크스루 결과
- 계정 권한·조직 설정·샘플 데이터에 따른 차이
- 실제 조직별 운영 규칙과 제품 설정에 따른 차이
- 데모 관찰만으로 사용자 만족도·이탈률·구매의향 확정 불가
- 임시 사용자 역할은 사용자 인터뷰 후 검증 필요
- 결제, 계약·외부 메시지 발송, 유료 전환, 계정 설정 변경, 최종 입양 상태 변경 미수행
- Petstablished는 가상 테스트 동물의 생성·수정·검색·삭제만 실행. 기존 운영 데이터 변경, 계약·결제·최종 입양·구매·계정 설정 변경 미수행
- Pawlytics는 외부 이메일 발송·최종 Outcome 실행과 임보자 직접 입력을 수행하지 않아 계약·결제·상태 변경의 완결성은 판단 보류
- 공유 데모의 초기 설정과 다른 사용자 데이터 변경에 따라 결과 변동 가능
