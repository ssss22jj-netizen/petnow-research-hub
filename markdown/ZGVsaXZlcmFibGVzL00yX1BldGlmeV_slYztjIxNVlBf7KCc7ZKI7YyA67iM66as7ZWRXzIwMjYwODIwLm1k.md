## 1. 결론 선행

| 항목 | 내용 |
| --- | --- |
| **제안 사항** | 산타바바라 카운티를 알파 디자인 파트너로 확보하고, 데모에서 시연한 화면을 **실데이터로 동작하는 알파 제품**으로 구현 |
| **MVP 정의** | 신규 기능 설계가 아니라 **기존 데모의 실물화**. 데모의 화면·개념은 유지하고 동작 기반(데이터·계산·저장·인증)을 신설 |

## 2. 배경 — 산타바바라 인터뷰에서 확인된 것

### 2-1. 확인된 문제

- 기존 shelter software의 **기능 부재가 아니라, 존재하는 정보가 현장 workflow와 연결되지 않아 '다음 행동'이 누락되는 문제**
- Sarah Aguilar(Director)가 제품 시연 전에 스스로 제기한 목표는 **Days of Care 단축**이며, 현재 spreadsheet·회의·Chameleon 우회 작업으로 관리 중
- 회의에서 결정된 task가 다음 주 회의까지 확인되지 않는 사례를 직접 제시. 이를 행정 비효율이 아니라 **동물의 보호일수 증가 요인**으로 인식

### 2-2. 제품 포지션에 관한 시사점

| 항목 | Sarah의 응답 | 시사점 |
| --- | --- | --- |
| Chameleon | 유지. Enforcement·Dispatch·Clinic·Shelter 업무가 이미 연결 | **대체 아닌 병행 레이어**로 진입 |
| Spreadsheet | 대체 가능 | 알파의 실질적 경쟁 대상은 spreadsheet |
| Petify 반응 | Needs Attention 화면에 즉시 긍정 반응 | 데모의 pathway 구조가 요구와 일치 |
| 도입 의향 | 실제 작동하고 가격이 적절하면 재원 확보를 검토할 의향 | 구매 의향의 전제 조건이 **실동작 확인** |

### 2-3. 이번 제안이 필요한 이유

- Sarah의 도입 검토 전제가 "제품이 설명한 방식대로 실제 작동하는지"이므로, **다음 접점에서 시연 수준을 한 단계 올려야 함**
- 현 데모는 백엔드·DB 없이 화면 시나리오를 구현한 상태이므로 실데이터 시연이 불가함
- 개발 기간 중 접점이 끊기면 리드 온도 하락이 예상되므로, **알파 테스터 통보 방식이 아니라 개발 과정에 참여하는 디자인 파트너 방식**을 권장 (5장 참조)

### 2-4. 경쟁 구도상의 근거

경쟁 제품 축 비교 결과, 이번 알파 범위는 **경쟁 제품이 비워 둔 구간**과 일치함.

| 제품 | 주무대 | 제품의 본질 |
| --- | --- | --- |
| Chameleon/CMS | 기관의 법적 의무 이행 전 구간 | 원장 — 면허·출동·수납·감사 기록 |
| 24PetShelter (동일 계열 신제품) | 출구(outcome) | 트랜잭션 — 입양 처리·체크아웃·칩 등록 |
| **Petify** | **보호 중(in-care)** | **준비 파이프라인 — 요건 판정·대기열·담당자** |

- 세 제품 중 **"동물이 보호 중인 동안 무엇이 진행 중인가"를 판정하는 층을 가진 제품이 없음**
- Chameleon의 보호 중 상태는 코드 한 칸 수준이며, 24PetShelter는 보호 중 관리에 해당하는 기능(포스터 관리·온라인 리스팅)이 미출시 상태
- 24PetShelter의 유일한 대시보드는 통계 대시보드이며 **작업 대기열이 아님**. 이는 수익모델(입양 1건당 $5 + 마이크로칩·보험 생태계)이 출구 거래를 우선하도록 강제한 결과로 판단됨 [의견]

**포지셔닝 표현**

- 차별점은 화면 통합이 아니라 단계 사이의 판정임. 24PetShelter도 동물 프로필 안에 여러 탭을 나란히 배치함
- 권장 표현: **"다음 단계로 넘어갈 수 있는지를 제품이 판정한다"**

## 3. MVP 스코프

### 3-1. 스코프 판단 기준

- 인터뷰에서 **Tier 1(최상위 신호)로 확인된 Animal Pathway 영역**만 포함
- Chameleon이 원장 시스템이므로 **동물 등록·의료·법 집행 영역은 제외**
- 임보자 커뮤니케이션은 Tier 2(강한 보조 신호)이므로 알파 2차로 이연

### 3-2. 알파 포함 범위

| # | 항목 | 데모 대응 | 작업 성격 |
| --- | --- | --- | --- |
| 1 | 동물 목록 — 현재 상태·확인 필요 사유·다음 행동·담당자·준비 상태 | Animals 목록 | 실물화 |
| 2 | 동물 상세 — 상태 배너 + 요건 체크리스트 + 다음 행동 카드 | Animal 상세 Overview | 실물화 |
| 3 | 확인 필요 대기열 — 조직 전체에서 조치가 필요한 동물 집계 | Dashboard | 실물화 |
| 4 | **요건 룰 편집** — 항목별 필수 여부·경과일 기준·수량 기준 | Settings 게시 요건 | 실물화 |
| 5 | **룰 계산 엔진** — 경과일·충족 여부 실계산 후 상태 자동 판정 | (데모는 고정 문자열) | **신규** |
| 6 | 담당자 배정 — 다음 행동에 담당자·마감일 지정 | Assign 모달 | 실물화 + 태스크명 자유 입력 |
| 7 | 완료 이력 — 변경·승인·상태 전환 기록 | Activity 탭 | 실물화 |
| 8 | **데이터 반입** — Chameleon 리포트 CSV 업로드 및 필드 매핑 | (데모 없음) | **신규** |
| 9 | **인증·역할** — Administrator / Reviewer / Publisher | (데모는 단일 계정 고정) | **신규** |
| 10 | 모바일 대응 — staff·volunteer의 현장 확인·완료 처리 | 반응형 5단계 구현 완료 | 검증만 |

> **4·5번은 기능 항목이 아니라 제품의 차별 엔진임**
>
> `조직이 준비 완료의 정의를 편집` → `룰이 상태를 자동 판정` → `미충족이 곧 대기열` → `대기열 각 행에 사유·담당자·다음 행동`
>
> 이 연쇄가 경쟁 제품에 없는 유일한 층이며, Sarah가 "I love it already"로 반응한 화면의 작동 원리임. 4·5번이 빠지면 나머지 8개 항목은 일반적인 동물 관리 화면으로 환원됨. **우선순위 최상위로 배치 권장**

### 3-3. 알파 제외 범위

| 항목 | 제외 사유 |
| --- | --- |
| 임보자 체크인 전 과정 (요청·모바일 폼·검토·반영) | Tier 2 신호. 알파 2차 1순위 후보 |
| 임보자 관리·배치 | 상동 |
| 외부 채널 게시 실행 | 산타바바라는 Chameleon 연계 게시 경로 보유. 알파에서는 **상태 판정까지만** 수행 |
| 신규 동물 등록 위저드 | Chameleon이 원장 시스템이므로 이중 입력 발생 |
| 입양 문의·매칭·결과 기록 | 인터뷰 미검증 구간 |
| Chameleon API 양방향 연동 | 레거시 Chameleon에 공개 API 부재. CSV 단방향으로 충분 |

### 3-4. 명칭에 관한 참고

- 데모의 체크리스트 명칭은 `Publishing requirements`(게시 요건)이나, 산타바바라는 게시를 Chameleon 경로로 수행할 가능성이 있음
- 해당 명칭은 **조직별 편집 대상**이므로, 알파에서는 기관이 자체 정의(예: 입양 준비 요건)할 수 있도록 문자열을 설정값으로 처리 권장

## 4. 기술 확인 사항

### 4-1. Chameleon 데이터 반입 경로 [검증 완료]

| 항목 | 확인 결과 |
| --- | --- |
| CSV export 지원 | **가능.** 단, 전용 버튼이 아니라 **Crystal Reports 경유** 방식 |
| 전체 데이터 일괄 덤프 | **불가.** Chameleon은 report 기반 추출 구조이며, 추출 범위는 리포트 정의에 종속 |
| 임의 필드 추출 | 커스텀 리포트 작성으로 가능. 업계 통계기관(Shelter Animals Count) 제출도 동일 방식 사용 |
| 공개 API | **부재.** API는 후속 플랫폼 24PetShelter에 예정, 레거시 Chameleon은 신규 개발 종료 상태 |
| 산타바바라 적용 가능성 | Sarah가 SQL·리포트 작성 담당자 역할을 겸하고 있어 커스텀 리포트 확보가 현실적 |

**설계 시사점**

- export 파일 형식을 당사가 통제할 수 없으므로 **필수 필드를 최소화하고 컬럼 매핑을 유연하게 설계**
- 주기 갱신은 수동 업로드 전제. 알파 단계에서는 주 1회 수동 업로드로 충분
- **개발 착수 전 실제 export 샘플 1건 확보가 일정 리스크의 최대 변수** (5-1 참조)
- CSV 경로는 임시 우회책이 아니라 **공공기관 대상의 지속 가능한 경로임.** 24PetShelter에 면허·현장출동·수납 기능이 없어 공공 고객의 Chameleon 잔류 가능성이 높으며, 이 경우 API 대기가 아니라 CSV 반입이 정식 연결 방식이 됨 [추정]

### 4-2. 개발 기간 [추정]

| 팀 규모 | 기능 완성 | 알파 투입 가능 (QA·초기 데이터 세팅 포함) |
| --- | --- | --- |
| 개발 2명 전담 | 4~6주 | **6~8주** |
| 개발 1명 전담 | 8~10주 | 10~12주 |
| 겸업 | 예측 불가 | 예측 불가 |

- 화면 설계·UI 구현물이 데모로 존재하므로 설계 비용이 절감됨
- 공수 집중 구간 3개: ①CSV 매핑(원본 데이터 상태에 종속) ②룰 커스터마이즈를 위한 스키마 유연성 ③volunteer 계정 체계
- volunteer 계정은 권한·온보딩 부담이 있으므로, 알파에서는 읽기 전용 링크로 범위 축소하는 방안 검토 가능
- **지배 변수는 스코프가 아니라 전담 인력 규모임**

## 5. 산타바바라 운영안

### 5-1. 사전 확보 자료

개발 착수 전 Sarah에게 요청할 항목이며, **요청에 대한 응답 여부 자체가 관심 강도의 측정 지표**로 기능함.

| 자료 | 용도 |
| --- | --- |
| Chameleon animal-level 리포트 CSV 샘플 1건 | import 스펙 확정. 미확보 시 매핑 설계 불가 |
| 현행 pathway spreadsheet의 컬럼 구조 | 요건 룰의 초기 설정값 도출 |
| Whiteboard 기재 항목 목록 | 현장 노출 정보의 우선순위 파악 |

- 실데이터가 아닌 **구조·형식만으로 충분**함을 명시할 필요가 있음. 카운티 정부 조직의 데이터 관리 규정 부담을 낮추기 위함

### 5-2. 관계 방식 — 디자인 파트너

| 구분 | 알파 테스터 | **디자인 파트너 (권장)** |
| --- | --- | --- |
| 상대의 역할 | 완성 후 사용 | 개발 과정에 요구사항 반영 |
| 수락 시 행동 | 없음 (대기) | 자료 제공·중간 피드백 |
| 개발 기간 중 접점 | 없음 | 3~4주 간격 진행 상황 공유 |
| 온도 유지 | 곤란 | 가능 |

- Sarah는 원하는 workflow를 to-do list·checklist 수준까지 스스로 구체화한 인터뷰이이므로, 요구사항 반영 제안이 부담이 아닌 참여 유인으로 작용할 것으로 판단
- 수락 시점에 **자료 제공과 다음 접점 일정을 함께 확보**하는 것이 핵심. 수락만 받고 종료할 경우 개발 기간이 공백으로 전환됨

### 5-3. 접점 구성 (2명 전담 기준)

| 시점 | 내용 |
| --- | --- |
| 착수 | 디자인 파트너 제안 · 자료 요청 · 다음 접점 예약 |
| +3~4주 | Sarah의 spreadsheet 구조가 반영된 요건 체크리스트·확인 필요 대기열 시연 후 피드백 수렴 |
| +6~8주 | 알파 투입 |
| 병렬 | 조달 경로 확인 (예산 책정 주체 · 조달 절차 · 재원 출처 · ROI 기준) |

- 카운티 조달 절차의 소요 기간이 개발 기간보다 길 가능성이 있으므로, 조달 확인을 개발과 병렬 진행할 경우 **제품 완성 시점과 예산 확보 시점을 근접**시킬 수 있음

## 6. 알파 성공 지표

Days of Care는 4주 단위로 측정이 어려우므로 선행 지표로 대체함.

| 지표 | 측정 내용 | 판정 의미 |
| --- | --- | --- |
| 요건 해소 소요일 | 확인 필요 상태 발생부터 해소까지의 기간 | pathway 정체 단축 여부 |
| 대기열 처리율 | 생성된 확인 필요 항목 대비 처리 건수 | 실사용 여부 |
| **Spreadsheet 이탈 여부** | 주간 동물 검토 회의가 Petify 화면으로 진행되는지 | **핵심 지표.** 대체 가능성의 직접 관측 |
| 사용자 주간 활성 | Sarah 외 staff·volunteer의 접속·처리 건수 | 조직 확산 여부 |

- Days of Care 실감소는 알파 이후 PoC 단계의 검증 대상으로 이연

## 7. 리스크와 결정 대기 사항

### 7-1. 리스크

| 리스크 | 내용 | 대응 방향 |
| --- | --- | --- |
| **경쟁 제품의 층 흡수** | 24PetShelter의 미출시 예정 기능에 **포스터 관리·온라인 리스팅·켄넬 카드**가 포함됨. 현재의 공백이 영속적이지 않음 | "지금 없다"를 "앞으로도 없다"로 진술하지 않을 것. 판정 층의 깊이(조직별 룰 편집·담당자 배정·감사 추적)로 방어 |
| **대외 표현과 구현 상태의 괴리** | 룰 계산은 현재 고정 문자열이며 실계산 미구현 (3-2의 5번) | 산타바바라 커뮤니케이션에서 "룰이 판정한다"를 현재형으로 진술하지 않을 것. 개발 예정 사항으로 명시 |
| **가격 경합 구도의 변화** | 24PetShelter는 **소프트웨어 정기 요금이 없음**(입양 1건당 $5 + 무료 마이크로칩) | 소프트웨어 구독료 부과 시 비교 대상이 됨. 다만 예산 항목이 달라 직접 경합은 아니며, 보완재 포지션도 가능 |
| **근거 폭 한계** | 24PetShelter 판단은 공개 화면 6점 + 기능 목록 기반이며, 대상은 단순 운영 조직용 초기 릴리스 | 확정 진술 회피. 추가 확인 경로 확보 |

### 7-2. 결정 대기 사항

| # | 항목 | 판단에 필요한 정보 |
| --- | --- | --- |
| 1 | **개발 전담 인력 규모** | 기간 추정의 지배 변수. 2명 전담 시 6~8주, 1명 전담 시 10~12주 |
| 2 | 알파 범위 확정 | 3-2 포함 범위 10개 항목의 조정 여부. 특히 **임보자 체크인의 알파 포함 여부** — 인터뷰 신호는 Tier 2이나, 경쟁 제품의 포스터 관리 출시 예정과 시점이 겹침 |
