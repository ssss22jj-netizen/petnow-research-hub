경쟁사 데모 시각 분석

기준일: 2026.07.29전문가 워크스루 + 사용자 리뷰 교차검증Shelterluv · Pawlytics · ASM · PawPlacer · Petstablished

기능 범위는 제품별로 유사하지만 사용성 차이는 과업 연결 방식에서 발생한다. 펫나우의 기회는 현장 기록이 동물 상태·담당자·후속 업무에 반영되기까지의 재입력과 수동 조정을 줄이는 데 있다.

분석 조건 · 한계 — 읽기 전에
  • 실제 사용자가 아닌 전문가 1명의 워크스루 — 사용자 만족도·이탈률 확정 불가
  • 제품별 운영 계정·무료 체험·로그인 데모의 권한과 조직 설정이 서로 다름
  • Pawlytics는 정식 운영 계정에서 가상 테스트 레코드로 검증. 외부 이메일 발송·최종 Outcome 실행과 임보자 직접 입력은 미수행
  • Petstablished는 37개 화면과 가상 테스트 동물의 생성·수정·검색·삭제를 검증. 계약·결제·최종 입양·구매·계정 설정 변경은 미수행
  • Shelterluv 임보자 계정·입양자 모바일 흐름 미검증 | Chameleon/CMS 별도 트랙
  • 임시 사용자 역할(R1~R4)은 Gina 인터뷰 후 검증 필요
검증 설계

임시 사용자 역할

  • R1 임보 운영 코디네이터 — 임보자 매칭·배치·상태 관리
  • R2 임보자 — 휴대전화로 사진·투약·행동 기록
  • R3 입양 코디네이터 — 신청·계약·결제·인계
  • R4 운영 관리자 — 전체 현황·누락·병목 확인

대표 과업

  • T1 신규 동물 등록 및 임보 배치 — 동물·임보자·위치·담당자 연결
  • T2 임보 중 상태 업데이트 — 투약·행동 기록과 후속 업무 연결
  • T3 입양 신청부터 인계 완료 — 신청자·계약·결제·동물 상태 갱신

동일 조건 및 측정 항목

  • 공통 데이터 — 동물 Milo, 임보자 Alex Kim, 입양 신청자 Jamie Lee
  • 정량 측정 — 완료 여부·시간·화면 전환·입력 필드·오류·막힘
  • 정성 판단 — 역할 적합성·상태 가시성·복구·연속성·모바일 완결성

R1~R4는 미국 쉘터 업무 흐름 조사에서 도출한 검증 전 역할 가설이며, Gina 및 미국 로컬 쉘터 인터뷰 후 수정 필요.

Petstablished는 테스트 동물 생성·수정·검색·삭제를 실행했으나 임보·의료·입양 전체 과업을 완주하지 않아 T1 시간 비교에서 제외.

상위 제품 판단
01
기능 추가보다 기존 CRM의 실행 부담을 줄이는 것이 진입 기회다
  • T1·T2·T3 관련 기능은 5개 제품에서 확인돼 기능 부재만으로는 진입 공백을 설명하기 어려움.
  • 정량 검증 4종의 T1 완료 시간은 ASM 2분 43초, Shelterluv 8분 44초로 최대 3.2배 차이. 입력 필드도 11~37개로 차이.
  • 리뷰에서는 데이터 이전·교육·외부 연동이 전환 장벽으로 나타나므로, 전체 CRM 교체보다 기존 시스템과 병행하며 실행 부담을 줄이는 접근을 우선 검증해야 함.
T1 타이밍 바 ASM: 입력 필드 11개 Shelterluv: 입력 필드 37개
02
검증되지 않은 공백은 모바일 화면이 아니라 임보자→운영자 업무 인계다
  • 5개 제품 모두 코디네이터와 관리자가 PC에서 기록하는 업무를 중심으로 설계.
  • Shelterluv는 일상 관찰 기록이 설정에 의존하고, ASM은 임보 중인 동물이 일상 관찰 목록에서 제외됨. Petstablished는 운영자 의료 기록에 임보 담당자를 연결하지만 임보자 직접 입력은 미검증.
  • 리뷰의 현장 기록 최신화·담당자 전달 문제를 함께 보면, 임보자 입력이 운영자 확인과 후속 업무로 연결되는 전체 흐름이 핵심 검증 대상임.
Shelterluv: 일상 관찰 기능 비활성 ASM: 임보 동물의 일상 관찰 목록 제외
03
모바일은 ‘화면 적응성’과 ‘역할별 과업 완결성’을 나눠 평가해야 한다
  • 화면 적응성: Pawlytics와 ASM은 데스크톱 화면을 축소해 터치 영역이 작고 가로 이동이 필요. PawPlacer는 390px에서 단일 열 카드로 재배치됐고, Shelterluv와 Petstablished는 운영자용 등록 화면의 반응형 구성을 확인함.
  • 역할별 과업 완결성: 임보자가 투약·행동 기록을 저장하고 운영자가 이를 확인해 동물 상태나 후속 업무에 반영하는 전체 과정. 입양자의 계약·결제 후 운영자 화면과 동물 상태가 갱신되는 과정도 포함.
  • 이번 검증에서는 5개 제품 모두 역할 간 전체 과정을 끝까지 확인하지 못함. Petstablished는 가로 스크롤이 없지만 등록 1단계만 1,674px 세로 길이여서 화면 재배치만으로 모바일 최적화를 판정할 수 없음.
PawPlacer: 단일 열 카드 구성 Pawlytics — 데스크톱 축소 ASM — 고밀도 축소 Petstablished — 단일 열·긴 세로 입력
04
동물 등록과 임보 배치를 따로 처리하면 위치·담당자 정보가 빠질 수 있다
  • 동물 등록과 임보 배치는 이어지는 업무지만 5개 제품 모두 별도 단계로 처리함.
  • Petstablished는 임보자를 지정하면 동물 상태도 Fostered로 변경된다는 결과를 실행 전에 안내해 상태 누락 위험을 줄임.
  • 펫나우는 임보 배치를 확정할 때 동물 상태·현재 위치·임보자·배치 시작일·담당 코디네이터·다음 확인 업무를 함께 저장하고 영향 범위를 사전에 안내하는 방식을 검증해야 함.
Shelterluv — 별도 이벤트 PawPlacer: 비교 제품 중 단계가 가장 적으나 2단계 필요
05
정상 처리 속도와 함께 실패·중단 후 복구 능력을 검증해야 한다
  • Pawlytics에서는 임보 위치와 동물 상태가 자동으로 맞춰지지 않았고, Shelterluv에서는 입력값 초기화와 저장값 불일치가 관찰됨.
  • 리뷰에서도 중복 입력·설정·이관 부담이 나타나 정상 경로의 처리 속도만으로 운영 적합성을 판단하기 어려움.
  • 저장 상태 표시와 함께 위치·상태 불일치 경고, 입력값 보존, 미완료 과업 재개를 검증해야 함.
Pawlytics: 임보 위치·상태 별도 변경 Shelterluv: 입력값과 저장값 불일치
정식 운영 계정의 가상 테스트 레코드에서 직접 확인한 결과
업무 플로우 인사이트 검증 — 데이터 계층에는 있고, 업무 계층에는 없다

업무 플로우 딥리서치의 인사이트 1(제품의 기본 단위는 단계가 아니라 동물·사건·상태 변화다)을 5개 제품 데모에서 확인한 결과. 이 원칙은 업계 데이터 표준이라 경쟁 제품의 저장 구조에는 이미 반영돼 있다. ASM은 동물 상세에서 입소·결과를 분리 관리하고 입양 완료 동물의 상태 수정에 Undo Adoption·Return Pet 절차를 강제하며, Shelterluv는 입양 1건당 $2의 사건 단위 과금을 쓴다. 격차는 이 구조를 현장 업무 흐름으로 꺼내주는 화면의 부재에서 발생한다.

근거 수준: 데모 직접 관찰과 리뷰 분석 종합. 각 제품의 내부 데이터 구조는 화면·공개자료 기반 추정.

01
레코드 편집 화면으로 회귀한다
  • 데이터는 사건 단위로 저장되지만, 사용자가 만나는 것은 동물 파일 하나를 열어서 고치는 경험.
  • Shelterluv 등록 양식은 필드 37개, ASM은 기본 정보·행동·위치·입소 결과·의료·문서 등 12개 섹션을 한 편집 화면에 연속 배치.
Shelterluv: 입력 필드 37개 ASM 검증 결과
02
다차원 상태를 분리하지 않는다
  • 법적·의료·행동·물리 위치·예상 결과·입양 공개 상태는 각각 따로 움직이는데, 경쟁 제품은 대표 상태 필드와 위치 정도만 두고 차원 간 동기화를 강제하지 않음.
  • 리뷰 반복 병목 1위인 위치·상태 불일치가 그 결과. 예외적으로 PawPlacer는 임보 배치 시 상태·위치·임보자·시작일을 한 화면에서 함께 저장.
PawPlacer: 임보 배치 단일 처리 Shelterluv: 결제 대기 중 상태 유지
03
상태 변화가 다음 행동을 만들지 않는다
  • 무엇이 이 동물의 다음 이동을 막고 있는가(차단 사유·담당·기한)를 보여주는 화면은 검증한 어느 제품에도 없음. 현장은 이 공백을 Population Rounds 회의로 매일 수동 보완.
  • 부분 채택 사례로 Petstablished는 임보자 지정 시 동물 상태가 Fostered로 함께 바뀐다는 것을 실행 전에 안내.
Petstablished: 상태 연결 안내 Petstablished: 신청 단계 분리
